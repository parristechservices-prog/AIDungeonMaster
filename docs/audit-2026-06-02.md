# Audit — 2026-06-02

Structured findings from a local play-test (no API keys), code review of `/api/turn` and prompts, and a line-by-line comparison against `ai-dm-app-gaps-and-next-steps.md`.

## Executive summary

The **hybrid architecture is sound** and the mock/table-rules path can complete a full one-shot when skill checks succeed. The main risks for real players are: **RNG-blocked scene progression** on failed checks, **dropped engine requests** due to a per-turn cap, **unnecessary LLM latency** when no keys are configured, and **docs/UI claiming features that are only partial** (ambient audio, appeal the DM).

## Mock play-test (no `GROQ_API_KEY` / `OPENAI_API_KEY`)

Environment: `npm run dev`, HTTP `POST /api/session/start` + `POST /api/turn`.

| Step | Expected | Observed |
|------|----------|----------|
| Session start | `social`, opening narration | OK |
| `hello` | Greeting, stay in social | OK — Mira greets |
| `I ask Mira about the courier` | Skill check + NPC update | **RNG-dependent** — on failure, stays in `social` with failure line |
| Retry social until pass | `exploration` | OK when roll ≥ DC |
| `I inspect the tracks` | Exploration check → `combat` on pass | OK |
| `I attack` ×2 | Engine combat, monsters to 0 HP | OK — matches Vitest regression with high rolls |

**Vitest regression** (`regression-flow.test.ts`) always passes because `Math.random` is mocked to `0.99`. **Live mock play** can stall on the first failed persuasion/perception roll until the player retries an “ask” or exploration phrase.

**Mock-only behaviors:**

- Fallback narration is prefixed with *"The wind shifts and the tale steadies itself."* (identifies table-rules mode; feels repetitive in-product).
- Mock does not set `ambient` (only LLM turns would).
- `what is my perception skill` (and similar) answers from state without engine rolls — good.

**Combat:** After one monster dies, the survivor can still attack on the next `monster_turn` — correct engine behavior.

## `/api/turn` pipeline

File: `src/app/api/turn/route.ts`

1. `getOrCreateSession(sessionId)`
2. `buildSystemPrompt(state)` + last **5** recaps appended
3. `generateDmTurn()` — Groq, then OpenAI fallback
4. On `null` → `deriveDmTurnFromInput()` (mock)
5. `runTurn()` → `validateNarrationAgainstState()` → `saveRecap` / dev log

**Strengths:** Clear fallback chain, recap memory in prompt, narration validator, structured dev logging.

**Issues found:**

| Issue | Severity | Detail |
|-------|----------|--------|
| LLM called with no credentials | Medium | Every turn awaits failed HTTP before mock; adds latency |
| `engineRequests.slice(0, 2)` | High | Mock social turn sends 3 requests (`skill_check`, `update_npc`, `add_canon_fact`); third is dropped |
| Fallback flavor prefix | Low | Hard-coded wind-shift line on every mock response |
| No output safety classifier | Medium | Described in `dm-prompt-design.md`, not implemented |
| Monolithic prompt | Low | Design doc describes classifier stack; V0 uses one system prompt |
| Appeal only in prompt | Medium | `[APPEAL]` documented; no play UI |

## Prompts (`system-prompt.ts`, `provider.ts`)

**Strengths:**

- Engine owns numbers; explicit rules against inventing HP/AC/dice
- Canon log + NPCs injected each turn
- DM personas (`DM_PERSONAS`)
- Appeals section for `[APPEAL]` input
- Groq `response_format: json_object`, `temperature: 0.1`, Zod validation on parse

**Gaps:**

- Prompt is inline TypeScript — versioning convention in `dm-prompt-design.md` not enforced in code headers
- `CORE RESPONSE RULES` numbering jumps (5–10; no 1–4)
- No post-generation safety pass on narration
- No separate intent-classifier / adjudicator prompts (acceptable for V0, doc drift)
